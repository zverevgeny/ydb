# TRUNCATE колоночной таблицы между чтением и записью в транзакции

## Наблюдаемое поведение

Транзакция с настройкой `SerializableRW` читает диапазон колоночной таблицы и
остаётся открытой. После `TRUNCATE` она записывает строку в ту же таблицу и
успешно завершается. Новое чтение видит только строку, записанную после
`TRUNCATE`.

Последовательность в тесте:

1. Создать колоночную таблицу и записать строку `(1, "before")`.
2. В KQP-сессии начать `SerializableRW`-транзакцию и прочитать диапазон,
   содержащий эту строку.
3. Провести `TRUNCATE` на ColumnShard, оставив транзакцию открытой.
4. В той же транзакции записать `(2, "after")` и выполнить commit.
5. В новой транзакции прочитать таблицу: видна только `(2, "after")`.

На уровне ColumnShard чтение регистрирует lock для старого `InternalPathId`.
`TRUNCATE` создаёт новое поколение с другим `InternalPathId`. Запись с тем же
lock попадает в новое поколение; проверка взаимодействий по новому
`InternalPathId` не находит чтение старого поколения, lock остаётся целым и
commit проходит.

Если клиенту будет доступна именно такая последовательность с полноценным
`TRUNCATE`, её нельзя упорядочить как последовательное выполнение одной
транзакции и `TRUNCATE`: транзакция видит старую строку, значит должна быть до
`TRUNCATE`, но её новая строка переживает `TRUNCATE`, значит должна быть после
него. Пока это **не доказательство нарушения клиентских гарантий**: в данной
ветке KQP отклоняет SQL `TRUNCATE TABLE` для колоночной таблицы. Тест обходит
SchemeShard и подаёт schema-транзакцию прямо в ColumnShard. Полный путь DDL
может дополнительно инвалидировать открытую транзакцию.

## Сделанные изменения

- `test_helper/shard_reader.{h,cpp}`: тестовый scan-reader умеет задавать
  `LockTxId` и `LockNodeId` для чтения с lock.
- `ut_schema/ut_columnshard_truncate_table.cpp`:
  `TruncateReadLockCanWriteNewGeneration` проверяет смену `InternalPathId`,
  сохранение lock старого поколения и успешную запись с тем же lock в новое.
- `ydb/core/kqp/ut/olap/locks_ut.cpp`:
  `TruncateBetweenReadAndWriteInSerializableTx` выполняет чтение, запись и
  commit через KQP-клиент. `TRUNCATE` проводится напрямую в ColumnShard,
  поскольку публичный SQL-запрос для колоночной таблицы ещё не поддерживается.

Оба теста намеренно фиксируют **текущее** поведение. Если требуемое поведение —
отклонить такую запись или commit, либо разорвать lock, их проверки нужно
изменить вместе с исправлением. В нынешнем виде тесты не стоит считать
регрессионной проверкой клиентской гарантии.
